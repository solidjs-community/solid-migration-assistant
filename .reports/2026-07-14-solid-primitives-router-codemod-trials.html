Solid Primitives and Solid Router expose critical first-pass gaps

Two parallel, isolated trials tested the current Solid 1 → 2 workflow against the latest verified Solid 1.x main revisions. Both projects had green Solid 1 baselines. Both migrations failed. The failures reveal library-manifest blind spots, unsafe shape rewrites, incomplete API validation, and a workflow runner that can report success for rejected output.

Cross-cutting critical findings

Critical

Package migration only recognizes the Kanban-style application manifest

Both libraries place Solid in devDependencies and expose compatibility through peerDependencies. The transform rewrote source and JSX configuration while leaving the root runtime/compiler graph on Solid 1. Primitives also contains 85 package manifests that need classification rather than one blanket pinning rule.

Required design: classify application, library, package, example, and excluded fixture manifests first. Refuse the source phase unless a coherent runtime, renderer, compiler, JSX, peer-range, and lockfile plan has been selected.
Critical

Validation is neither authoritative nor complete

In Primitives, the validation node detected blockers but the workflow returned success. In Router, the direct validator itself missed removed APIs, invalid splitProps output, legacy contexts, stale JSX ownership, and a broken dependency graph. Textual residual checks also falsely treated the string {"<Index>"} as JSX while missing a multiline directive.

Required design: make validation AST- and binding-aware, validate manifests/config before source, add a compile gate, and treat runner exit propagation as unsafe until independently enforced.
Critical

Some supported-looking rewrites generate invalid or semantically wrong code

Primitives exposed a lifecycle rewrite that drops a closing parenthesis, object-valued directives that become non-returning blocks, duplicate ref attributes, and binding-unaware const merge = merge(...). Router exposed invalid destructuring after splitProps → omit and incomplete classList normalization.

These shapes need focused red fixtures before implementation fixes. A migration must never present syntactically invalid output as a successful node.

Recommended fix order

  1. Add a discovery/classification phase. Inventory all manifests, package roles, package-manager/workspace layout, Solid ranges, compiler packages, renderer ownership, SSR usage, and project references. Produce a migration plan before editing.
  2. Make unsafe package shapes block immediately. Support dependencies, devDependencies, and deliberately selected peerDependencies; distinguish publishable libraries from applications and examples.
  3. Harden validation and exit semantics. Add AST residual rules for every removed API, directive, provider, JSX owner, and old signature. Run direct validation plus parse/type gates; never trust the outer workflow exit alone.
  4. Fix syntax- and binding-safety defects first. Lifecycle parentheses, object-expression directive returns, duplicate refs, multiline directives, import/local binding collisions, and splitProps semantics each need red fixtures.
  5. Add library-specific semantic recipes. Router-style async compatibility layers, context APIs, memo signatures, owned-scope writes, class normalization, event delegation, bundler externals, and JSX public types require explicit decisions rather than broad renames.
  6. Require first-pass idempotency. Ordering bugs should fail a test that hashes every changed file after one and two workflow runs.
  7. Promote both repositories into a corpus gate. Start with parse + blocker expectations, then narrow the blocker count as each supported shape gains a fixture and semantic test.
