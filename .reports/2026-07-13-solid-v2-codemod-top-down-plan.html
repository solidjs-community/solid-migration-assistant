Planning report · 13 July 2026

Plan the codemod as a decision pipeline, not a bag of rewrites.

The existing six-package split is a useful implementation skeleton. The missing top-level design is the workflow contract around it: discover the target, preserve the evidence, make each migration decision explicitly, surface uncertainty, then verify the migrated program with Solid 2 diagnostics.

Target docs/runtime: Solid 2.0.0-beta.17 Solid commit: a51cac19 Project branch: fresh-solid-v2-rewrite Current transforms: scaffold / no-op

Recommendation

Make the workflow own seven stages and a stable decision vocabulary.

Keep Safe Mechanical Migration as the default product. Add a read-only inventory before any edits, and add diagnostics plus a Migration Report after the edits. Inside the transform packages, define every rule using the same contract: evidence, classification, action, fallback, idempotency, and verification.

This turns the recipe into a coherent migration system. A user can explain why an edit happened, why another site was left for review, which Solid 2 assumption it used, and what must run before the migration is considered done.

What the Solid docs imply for this project

The source of truth is volatile

The checked-in Solid repository is now on 2.0.0-beta.17. The codemod must pin a Compatibility Manifest to a Solid docs/runtime revision rather than encode an unqualified idea of “Solid 2”.

Migration is not one confidence level

The docs mix direct package moves, syntax-preserving renames, context-sensitive compatibility rewrites, intent-dependent redesigns, and runtime-only diagnostics. Treating all of them as AST rewrites would be unsafe.

Renderer ownership is a package decision

jsxImportSource, JSX types, package placement, and runtime import paths depend on a package’s Target Profile: web, hyperscript, custom renderer, or renderer-neutral library.

Diagnostics are part of migration

Solid 2 exposes structured diagnostic codes. Static transforms cannot reliably find all top-level reads, owned writes, pending async reads, lifecycle errors, or ownership leaks. The workflow needs a Diagnostic-Driven Migration phase.

Correct the current batch assumption before implementation

The project glossary currently says batch can be safely renamed to flush. The migration guide—unchanged through beta.17—says something materially different: Solid 2 batches by default, so most batch(fn) wrappers should disappear. flush() or flush(fn) is only justified when code requires immediate reactive or DOM visibility. A blanket rename would preserve synchrony that may no longer be necessary and would overuse a forcing primitive.

Proposed resolution: redefine Flush Boundary as a proven synchronous-observation boundary. Classify ordinary batch sites as “remove wrapper”, sites followed by immediate reads/DOM operations as “insert/retain flush”, and ambiguous sites as review.

Current scaffold: good bones, missing ends

The recipe already separates JSON/config, imports, JSX types, JSX shapes, runtime-safe edits, and review markers. That is a reasonable publishable-package layout. What it does not yet model is the information flow before and after those transforms.

Beta.15 → beta.17 update audit

The Solid checkout fast-forwarded from a4ca10b7 (2.0.0-beta.15) to a51cac19 (2.0.0-beta.17). The range contains 214 changed files and is dominated by async, optimistic-state, store, SSR, hydration, and error-handling correctness work. The main migration guide, RFCs 01–07 and 09, and the package cheatsheet did not change. RFC 08 gained one lifecycle diagnostic. Consequently, the workflow architecture and most decisions remain valid; the changes below are targeted amendments rather than a redesign.

Beta.16/17 differenceCodemod consequencePlan update
All Solid packages advanced to 2.0.0-beta.17. The Compatibility Manifest and generated dependency ranges must target one coherent beta.17 package set. Re-pin the target and source commit; include related @dom-expressions/* versions.
New ACTION_CALLED_IN_OWNED_SCOPE dev error. An action() invocation is invalid when called synchronously from a component body or computation. Actions remain valid in handlers, effect apply callbacks, tracked effects, onSettled, and other imperative scopes. Add a diagnostic mapping and a conservative static candidate scan. Never relocate an action call without intent.
New documented SETTLED_CLEANUP_UNOWNED dev error. An onSettled callback may return cleanup only when it was established from an owned scope. Out-of-band one-shot callbacks may not return cleanup. Lifecycle decisions must prove both callback shape and call-site ownership—not merely rename onMount.
Effect-bundle error now runs as the queued error arm of the effect phase and receives the original thrown value. Writes in the error handler are valid imperative-phase writes; errors that recover before apply do not call the error arm. Effect-phase throws still escalate to a boundary. Update effect fixtures and guidance. Do not flag writes in an effect-bundle error arm as owned-scope writes.
Active optimistic overrides now deliberately report isPending === false. isPending cannot be generated as a generic “Saving…” flag for an optimistic action. User-decreed optimistic state is considered settled. Resource/action recommendations must use co-written optimistic status data or a separate createOptimistic(false) flag for mutation affordances.
Uncaught reactive errors now emit REACTIVITY_HALTED and permanently stop later writes/flushes; resetErrorHalt() is exposed for test/dev tooling. A diagnostic run can poison the remaining verification process after one uncaught error. Run diagnostic scenarios in isolated processes/roots or reset the halt state between controlled test captures.
dom-expressions packages moved under the @dom-expressions scope; SLD was renamed to Tagged JSX. Most Solid users are insulated by @solidjs/*, but direct dependencies/imports need migration: runtime, JSX plugin, hyperscript, and tagged-JSX packages. Add optional direct-dependency decisions to config/import normalization; keep them gated on proven direct usage.
createErrorBoundary/createLoadingBoundary now infer Accessor<T | U>; createProjection seed inference was corrected. These are type-surface fixes, not source migrations. Pin beta.17 in typecheck fixtures and avoid adding compensating casts that beta.17 no longer needs.
Large runtime hardening across async iterators, thenables, latest/isPending, nested boundaries, stores, reconcile, lazy SSR, streaming, and hydration. No new general AST rewrite follows, but beta.15-based verification could have produced false regressions or missed failures. Expand real-repository verification with SSR/hydration, nested Loading/Errored, optimistic refresh, array holes/symbol keys, and async rejection cases.

Net result

The first-release scope does not need to grow dramatically. The main additions are three diagnostic codes, ownership-aware onSettled handling, correct optimistic pending guidance, direct dom-expressions package moves, and a tougher verification matrix. The beta.15 decisions about imports, JSX ownership, control flow, stores, resources, DOM, and the batch/flush distinction still stand.

Proposed top-down workflow

The important change is that edits do not begin until the workflow has captured the original package evidence. Each later stage consumes that snapshot and emits decisions.

0
Preflight contract
Select compatibility target and mode; require a clean worktree; identify workspace/package roots; record available package manager and checks.
Output: run manifest
1
Inventory & profile
Read package/config/source evidence without edits. Classify package role and Target Profile. Inventory Solid APIs, JSX modes, renderer imports, and semantic migration clusters.
Output: immutable evidence snapshot
2
Package & module normalization
Apply role-aware dependency changes, config changes, import path moves, and proven direct API renames against the captured profile.
Output: normalized dependency/import graph
3
Renderer & JSX migration
Move renderer-owned JSX types, preserve renderer-neutral public types, and apply local-safe JSX/component shape changes.
Output: renderer-correct source
4
Runtime decisions
Handle safe lifecycle/store/reactivity patterns. Use compatibility rewrites where they preserve behavior. Do not guess at effects, resources, ownership, or public API intent.
Output: mechanically migrated program
5
Semantic audit
Scan the post-transform tree for unresolved sites. Add deduplicated, coded Review Markers and populate the report with evidence and suggested choices.
Output: explicit review queue
6
Verification loop
Install if authorized; format; typecheck; test; build; capture Solid 2 diagnostics; check idempotency; rerun after fixes.
Output: verified or blocked report

First technical spike: can recipe stages share an artifact?

The ideal workflow writes a run manifest in stage 1 and every later package reads it. Validate this against Codemod workflow capabilities before building the analyzer. If artifact passing is unavailable, keep the conceptual phase but implement profile inference as deterministic shared helpers from the nearest package/config files, and generate the consolidated report in a wrapper command around the recipe.

Workflow invariants

  • No edit may depend on evidence that an earlier edit has already destroyed; inventory is captured first.
  • Every edit records a decision code and source rule, even if the user sees only the diff.
  • Every ambiguous site has a stable fallback: leave source intact, add a Review Marker, record evidence.
  • Every transform is idempotent independently and in the composed workflow.
  • Already-migrated and mixed 1.x/2.x code is valid input.
  • Library public APIs are preserved unless the user explicitly enables breaking public API edits.
  • The report distinguishes “transformed”, “review required”, “diagnostic required”, “skipped”, and “verified”.

Execution modes

Audit

Inventory only

Classify packages and sites, estimate scope, and produce a report. No source edits. This is valuable before adopting a beta target or planning a monorepo migration.

Safe migration · default

Mechanical + review

Apply only proven edits and compatibility-preserving transformations. Add Review Markers for intent-dependent work. This should be the first reliable release.

Future

Best-effort AI

Resolve selected semantic sites using whole-project context. It should consume the safe migration report, be explicit opt-in, and never rewrite review-only categories.

Do not build a large shared framework first

Extract shared helpers only after the same proven need appears in two focused rules. The first vertical slice should establish the minimal contracts—decision records, binding provenance, import edits, and profile lookup—then grow shared code from tested usage.

Make review markers actionable and machine-readable

A generic file-level TODO(solid-2) is easy to add but hard to resolve. Use stable decision codes and one concise local instruction, while keeping richer evidence in the report.

// TODO(solid-2 S2-EFFECT-001): Split this effect into tracked compute and untracked apply phases.
// Evidence: reads [userId, store.user]; side effects [fetch, setTitle]; cleanup [abort].

// TODO(solid-2 S2-RESOURCE-001): Migrate this Resource Cluster as one unit.
// Report: resource "user" has loading, error, refetch, and mutate consumers.
  • Deduplicate by decision code and AST anchor.
  • Prefer the narrowest statement-level marker; use file-level summaries only for dispersed clusters.
  • Never rewrite or duplicate an existing marker on rerun.
  • Include a suggested verification action, not an asserted replacement, for semantic sites.
  • Generate JSON alongside HTML so follow-on tools can consume unresolved sites.

Composed workflow tests

  1. Workspace fixtures that require several packages in sequence—not only isolated rule fixtures.
  2. Snapshot the decision report as well as transformed files.
  3. Run the complete recipe twice and assert a clean second diff.
  4. Assert no remaining removed import paths or direct-safe API names.
  5. Assert every known semantic candidate is either transformed or represented by exactly one marker/report entry.
  6. Run error-producing diagnostic scenarios in isolated processes/roots or call the test/dev resetErrorHalt() between controlled captures so one uncaught error cannot invalidate later checks.

Real-repository proving loop

Use the supporting repositories in increasing difficulty, with clean pinned commits:

  1. test — tiny controlled app; prove the orchestration and report.
  2. powerchat — application profile and async/UI behavior.
  3. solid-router — library/public API and renderer interactions.
  4. solid-primitives — ownership, lifecycle, primitive internals, broad package matrix.
  5. kobalte — large component library, directives, polymorphism, event and type complexity.

Definition of done for a release

  • All rule and workflow fixtures pass, including idempotency.
  • Workflow metadata validates and every package declares the same target ruleset.
  • At least one web app and one published library complete the Verification Loop.
  • No unexplained Solid 2 error diagnostics remain; warnings are resolved or recorded.
  • SSR/hydration checks cover nested Loading/Errored boundaries, async rejections/thenables, lazy modules, and post-hydration refresh.
  • Every Review Marker has a stable code and corresponding report entry.
  • The root documentation describes the actual recipe and its safety boundary.

Recommended implementation roadmap

Build vertical slices through the workflow. Each slice should leave the recipe runnable and more truthful than before.

Workflow contract and source-of-truth

Write the beta.17 Compatibility Manifest, Target Profile evidence rules, decision schema, marker format, run/report schema, and corrected Flush Boundary definition. Include direct @dom-expressions/* mappings and the new diagnostic codes. Update the stale root README.

Exit: metadata tests assert the seven conceptual stages, manifest revision, and package responsibilities.

End-to-end tracer bullet

Use one web app fixture. Analyze its profile, migrate solid-js/web to @solidjs/web, update package/config from the manifest, emit a decision report, and prove a clean second run.

Exit: one complete migration path—not just a transform unit test—works.

Module and renderer normalization

Finish import paths, dependency roles, JSX config, renderer-owned type imports, collision handling, and renderer-neutral Element cases.

Exit: web, hyperscript, custom-renderer, and library profiles have explicit fixture coverage.

Local-safe JSX shapes

Implement Loading/Errored, Index/For, literal Reveal mappings, Context providers, class composition, and conservative attributes. Add binding and shadowing helpers only as repeated needs emerge.

Exit: all direct-safe and proof-required JSX fixtures pass in isolation and composed order.

Runtime-safe and compatibility layer

Implement produce removal, path setter compatibility, unwrap/snapshot, rest-only splitProps, lifecycle cleanup shapes, memo initial-prev patterns, and conservative batch classification.

Exit: no rule rewrites an ambiguous semantic site merely to make the fixture green.

Semantic audit and diagnostics

Add effect, resource, transition, root ownership, directives, once markers, createMutable/selector, and unsupported DOM scans. Integrate Solid DEV.diagnostics capture.

Exit: the report is a complete migration queue rather than a collection of generic TODOs.

Real-repository hardening and beta drift

Run the proving loop, classify failures by decision code, expand fixtures before fixes, and add a manifest update procedure for each Solid beta.

Exit: release evidence includes representative app and library migrations with known residual work.

Explicitly defer from the first safe release

  • General automatic effect splitting.
  • Whole Resource Cluster rewrites and automatic optimistic action design.
  • General createComputed, createMutable, or createSelector redesign.
  • Automatic directive-definition restructuring.
  • Automatic ownedWrite: true insertion.
  • Best-Effort AI Migration.
