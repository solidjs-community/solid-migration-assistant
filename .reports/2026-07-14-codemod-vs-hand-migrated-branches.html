The hand migrations are architectural rewrites, not larger search-and-replace patches

This analysis compares the current codemod output against the existing Solid 2 migration branches for Solid Router and Solid Primitives. Router provides a clean same-base comparison. Primitives provides a broader package-by-package migration history, but its long-running branch and intentional Solid 1 exclusions require a scoped comparison rather than a raw tree verdict.

DESIGN GAP

The codemod covers syntax surfaces; the successful migrations encode project decisions.

Mechanical import, renderer, lifecycle, class, and test-setup edits do match in a small set of files. The decisive differences are dependency topology, public API redesign, async and ownership semantics, package scoping, test strategy, and intentional deletion. Those decisions need explicit workflow phases and AI/manual escalation rather than more global AST patterns.

Version caveat

Do not copy Router's beta.7 JSX configuration blindly

Router next remains on Solid beta.7 and keeps jsxImportSource: "solid-js". The beta.17 documentation and Primitives beta.17 branch use @solidjs/web. The codemod's renderer ownership direction is therefore newer than this one Router setting, even though its broader Router migration is invalid.

This confirms a workflow rule: validate only the package/file set declared in scope, while separately reporting excluded legacy islands. A repository-wide “no old token anywhere” check produces both false positives and pressure to mutate intentionally unmigrated code.

What the codemod already gets right

Exact Router matches

  • src/lifecycle.ts
  • src/routers/Router.ts
  • src/routers/StaticRouter.ts
  • test/setup.ts

These are narrow renderer/lifecycle/test-setup shapes with little application-specific state reasoning.

Useful broad coverage

  • Renderer import movement
  • Many store import and snapshot conversions
  • Intrinsic class conversion
  • Some Index conversions
  • Conservative effect/store blockers
  • Idempotent Router output

The mechanical layer is worth retaining as one phase after project classification.

Changes this comparison should drive in the codemod plan

  1. Add a project and package discovery phase. Build a graph of workspaces, applications, publishable libraries, examples, tests, dev-only surfaces, peer ranges, and intentionally excluded Solid 1 islands.
  2. Create a migration manifest before editing. For each package, record target beta tuple, renderer, compiler, peer policy, public API compatibility, SSR mode, and validation commands.
  3. Split mechanical AST work from semantic recipes. Imports and proven JSX forms can be deterministic. Effects, async data, ownership, router transitions, directive APIs, and library prop utilities require recipe-specific preconditions or AI/manual work.
  4. Migrate symbol families transactionally. A directive migration must update its definition, exported type, imports, call sites, documentation examples, tests, and ref composition together.
  5. Support deletion and redesign outcomes. The correct Router migration deleted an obsolete async layer; the correct Primitives branch deleted many dev modules. “Translate every file” must not be the only outcome.
  6. Make dependency/config migration role-aware. Handle dev and peer dependencies, lockfiles, bundler externals, compiler module names, and beta-version-specific JSX ownership. The Primitives beta.17 branch uses plugin 3.0.0-next.5, not the codemod's global next.4 pin.
  7. Use hand branches as decision corpora. Extract focused before/after fixtures from individual migration commits instead of using entire current trees as exact golden output.
  8. Validate in layers. Parse → residual AST checks → package graph → typecheck → build → focused behavior → full package tests. Enforce node failure independently of the current workflow runner's exit code.

Bottom line: keep the current deterministic transforms as a narrow mechanical phase. The hand branches show that successful Solid 2 migration is organized around package classification, explicit compatibility decisions, semantic redesign, deletion, and behavior tests. Those belong in the workflow before the codemod can generalize beyond its Kanban fixture.
