2. Structural & Implementation Gaps

2.1 Import Source Coverage

15 of 17 import-checking rules only check solid-js; only 2 check solid-js/web. APIs like onMount, createEffect, and others are also importable from solid-js/web in Solid 1.x projects. When a user imports from solid-js/web, these rules silently pass.

2.2 Import Syntax Coverage

The findImportedCalls helper supports named imports, aliased imports, and namespace imports (import * as Solid). The import-path rules (beta32-subpaths, web-import) use manual import-statement scanning and cover named imports only. No rule covers:

Re-exports: export { createEffect } from "solid-js"
Dynamic imports: import("solid-js/web")
CommonJS require: require("solid-js/web")
TypeScript import type expressions: import("solid-js").JSX
Indirect/forwarded calls through wrappers, HOCs, or module re-exports

2.3 Project-Level Analysis (Roadmap Gaps)

tsconfig.json analysis: No detection of jsxImportSource, JSX configuration, or renderer package type ownership.
package.json analysis: No detection of Solid version pins, renderer packages, or dependency compatibility.
Monorepo workspaces: No cross-package analysis; each file is analyzed in isolation.
Cross-file alias tracking: Only component-renames uses cross-file references. Other rules analyze per-file.
SSR entry points: No detection of renderToString, renderToStream, or server-specific APIs.

2.5 createEffect 2-Arg Case: The Critical Silent Gap

The create-effect rule filters to only 1-argument calls. A 2-argument call like createEffect(fn, 0) — where the second argument is an initialValue — is silently skipped. The user gets no warning that their initialValue must be migrated into a default parameter. This is the single most dangerous gap in an otherwise well-structured analyzer because it produces a false sense of completeness: the file passes analysis but has an unaddressed migration site.

5. Recommendations

5.1 Critical: Fix the createEffect 2-Arg Gap

The create-effect rule should detect all createEffect calls and provide differentiated guidance:

1-arg: split into compute/apply (current behavior)
2-arg where second arg is not a function (initialValue): warn about moving to default parameter
2-arg where second arg is a function (already split): pass silently or acknowledge
3-arg (fn, initialValue, options): detect and guide

5.2 High-Impact: Add solid-js/web Import Source Coverage

Extend findImportedCalls to accept an array of module sources, or add a wrapper that checks both solid-js and solid-js/web. This would close the import-source gap for 14 rules with a single shared-code change.

5.3 Priority: Resource Tuple Destructuring

Add detection for resource.loading, resource.error, resource.refetch(), and resource.mutate() patterns. These are commonly hit in real Solid 1.x codebases and have no guidance from the current analyzer.

5.4 Medium-Impact: onCleanup Detection

Detect onCleanup() calls within createEffect/onMount callbacks and guide users to return cleanup functions instead. This is a high-frequency pattern in real code.

5.5 Medium-Impact: Non-Static Import Forms

Add detection for re-exports, dynamic imports, and require() calls in the import-path rules. The roadmap explicitly calls this out.

5.6 Lower-Priority: New-Surface Gaps

Most of the remaining 33 uncovered items fall into three buckets:

New APIs (Reveal, Repeat, action, createOptimistic, etc.) — not migration sites; no detection needed
Structural/behavioral (post-setter reads, cleanup timing, delegated events) — cannot be detected statically; needs runtime validation
Project-level (tsconfig, package.json, monorepo) — needs new analysis infrastructure
