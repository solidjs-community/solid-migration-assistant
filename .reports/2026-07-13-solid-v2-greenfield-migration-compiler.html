From-scratch architecture · 13 July 2026

Build a migration compiler, not a sequence of codemods.

A Solid 1.x → 2.0 migration is a workspace-wide reasoning problem with edits inside it. The greenfield system should analyze once, persist evidence and decisions, schedule dependency-ordered changes, and use compiler/runtime feedback to converge safely.

Target: Solid 2.0.0-beta.17 Solid revision: a51cac19 Current repository structure intentionally ignored Independent fresh-context review incorporated

Core architecture

A version-pinned, resumable migration compiler

A semantic analyzer discovers the workspace and produces evidence-backed findings. A decision planner resolves each finding into an automatic action, an approval, a design choice, or a blocker. A transaction engine applies dependency-ordered patches. A verification engine converts type, build, test, browser, SSR, and Solid diagnostic results into new evidence. The cycle repeats until every finding is resolved or explicitly accepted.

AnalyzeWorkspace graph, symbols, effects, resources, renderers, public contracts, commands
PlanFindings, evidence, alternatives, risk, dependencies, verification obligations
DecidePolicy, automatic choice, human approval, semantic design, waiver, blocker
ApplyAtomic patch waves with preconditions, journal, reverse patch, reanalysis
VerifyTypes, builds, tests, browser/SSR scenarios, DEV diagnostics, idempotency
Verification observations become findings; affected findings are replanned and reapplied until convergence.

AST rewriting remains useful, but it is downstream infrastructure. The authoritative product is the evidence/decision history and the verified target state—not a count of renamed identifiers.

Design principles

Pin the meaning of “Solid 2”

Rules target an exact Solid release family and source revision. Unknown future betas may be audited, never silently auto-applied.

Baseline before touching code

Pre-existing failures are evidence, not migration regressions. Capture types, builds, tests, and smoke scenarios first.

Evidence before confidence

A rule records positive and negative evidence. Confidence is multidimensional; a high-confidence, high-risk edit can still require review.

Graph, not global order

Each change declares prerequisites and verification gates. The scheduler derives waves rather than hard-coding one universal transform sequence.

Transactions, not mutation

Rules propose edits. One engine resolves overlaps, validates preconditions, journals outcomes, and owns rollback.

Finish with proof

“No old API names” is not success. Every finding needs a disposition and every behavioral decision needs a verification obligation.

Non-goals for the first system

  • Automatically redesign every effect, resource, directive, or mutation workflow.
  • Force every package into one renderer label.
  • Use source TODO comments as the canonical migration database.
  • Declare success because source parses or because a single fixture test passes.
  • Support an unbounded range of evolving Solid betas with the same rules.
  • Hide missing tools, skipped commands, or unverifiable behavior behind a green status.

The user journey

The workflow should be useful before the user permits edits and resumable after every interruption or design decision.

# 1. Read-only: pin target, discover workspace, capture baseline, build findings
solid2-migrate analyze --target 2.0.0-beta.17

# 2. Review the generated plan and unresolved design choices
solid2-migrate plan --open

# 3. Apply only deterministic, policy-approved changes
solid2-migrate apply --mode safe

# 4. Resolve a semantic work queue interactively or by editing decisions.jsonl
solid2-migrate decide

# 5. Apply newly unblocked transactions and verify
solid2-migrate continue

# 6. Run the complete target verification contract
solid2-migrate verify --full

# Recovery and automation
solid2-migrate status
solid2-migrate rollback --transaction <id>
solid2-migrate verify --ci

Exact workflow phases

Lock the target contract

Pin Solid core, renderer, compiler, related DOM-expression packages, rule-pack revision, and the Solid source commit. Snapshot public exports, relevant type signatures, JSX ownership, documented removals, diagnostics, and release deltas.

Output: target-lock.json. Gate: every selected version belongs to one supported compatibility bundle.

Discover workspace topology and validation surfaces

Find package/workspace boundaries, dependency graph, tsconfig inheritance, aliases, source/generated/vendor exclusions, entry points, browser/server/test execution contexts, public exports, and existing commands.

Output: workspace.json. Gate: ambiguous package roots or generated-source policies must be resolved before edits.

Capture the source baseline

Run available typechecks, builds, tests, SSR/hydration checks, and selected user flows before edits. Record failures, runtime versions, command lines, duration, output hashes, and unavailable prerequisites.

Output: baseline.jsonl. Gate: “not run” and “blocked” remain distinct from pass.

Build the semantic inventory

Create typed programs and symbol indexes. Detect migration surfaces: packages/imports, JSX ownership, props, control flow, contexts, effects, lifecycle, ownership, stores, resources, transitions, actions, directives, DOM namespaces, SSR and test-time immediate-read assumptions.

Output: initial findings.jsonl. Gate: a same-named local function is never confused with a Solid API.

Enrich findings into migration units

Connect related sites across files: resource creation/read/loading/error/refetch/mutate/boundaries; effect reads/writes/cleanup; context definition/providers/consumers/public wrappers; directive definitions/consumers; store initialization/setters/mutations; render roots/events/portals.

Output: evidence-complete clusters. Gate: cross-file behavior is planned as one unit, not a list of call-site rewrites.

Resolve decisions

Evaluate rule evidence and policy. Persist automatic decisions, approvals, selected alternatives, waivers, and blockers. Present concrete 2.0 alternatives and their verification requirements instead of generic “review this” flags.

Output: decisions.jsonl. Gate: no unresolved design decision is smuggled into a deterministic transaction.

Construct the change DAG

Turn resolved findings into changes with prerequisites, affected symbols/files, conflict sets, verification obligations, and rollback boundaries. Example dependencies: target lock → dependency alignment → install → renderer types → JSX checks; resource design → boundary edits → mutation UX → async scenarios.

Output: plan.json. Gate: cycles are surfaced as plan errors or grouped into one atomic migration unit.

Apply transactional waves

For each ready wave, verify pre-edit hashes and semantic preconditions, merge non-overlapping edits centrally, write a forward and reverse patch, apply atomically, format only touched files, and reanalyze affected programs.

Output: changed source, journal.jsonl, and patches/. Gate: stale evidence or overlapping proposals abort the transaction instead of producing a best guess.

Verify cheaply, then deeply

After each wave, run targeted parse/type/rule checks. At checkpoints, run package tests/builds. For semantic waves, run browser, SSR, hydration, and Solid diagnostic scenarios. Convert every failure into a normalized observation linked to the responsible findings and transactions.

Output: diagnostics.jsonl and verification.jsonl. Gate: migration regressions block downstream waves unless explicitly waived.

Converge and close

Replan from new evidence, apply newly unblocked changes, and repeat. Close only when all findings are resolved, explicitly waived/accepted as debt, or blocked with named missing evidence. Run full verification and idempotency last.

Output: final state ledger plus human-facing HTML report. Gate: complete disposition and proof, not zero string matches.

The durable migration model

The system must survive restarts, target updates, manual edits, and partial rollbacks. JSONL/event-like artifacts make state appendable and auditable. The HTML report is a projection, not the database.

Use capability facets, not one package profile

A package can be a published library, use web JSX internally, ship renderer-neutral types, include server entries, and have browser-only tests at the same time. A single “web/library/custom renderer” label loses information and forces wrong edits.

FacetExample valuesDecisions it informs
Distribution rolePrivate app, published library, renderer, tool, test-only packageDependencies vs peers, public API preservation, install behavior
Renderer capabilityWeb, hyperscript, custom, renderer-neutral, mixedJSX source, renderer-owned types, runtime imports

Async/render behaviorCSR, hydration, streaming SSR, static SSR, islandsBoundary placement, lazy assets, verification obligations
Validation coverageTypecheck, unit, browser, SSR, noneReview threshold and required added scenarios

Package-level facets provide defaults; file, entry-point, and symbol-level evidence can override them. Mixed evidence is a first-class state, not a failure to classify.

Decision and confidence model

Do not compute one magic confidence percentage. Track dimensions independently and combine them with behavioral risk.

Evidence dimensions

  • Identity: is this definitely the Solid symbol across aliases/re-exports?
  • Shape: does syntax match a supported transformation form?
  • Semantic uniqueness: is there one behavior-preserving target?
  • Context coverage: are renderer, owner, SSR, async, and public contract known?
  • Validation strength: can relevant behavior be exercised?
  • Behavioral risk: what is the cost of a wrong choice?

Required rule contract

  • Supported source and target ranges
  • Detection and resolved-symbol requirements
  • Positive and negative evidence
  • Candidate decisions and behavioral tradeoffs
  • Preconditions and edit proposals
  • Conflict set and DAG dependencies
  • Verification obligations and rollback scope
  • Idempotency and invalidation conditions

High confidence does not cancel high risk

The tool can be certain that a component is Suspense while still lacking enough evidence to redesign loading/revalidation UX around its resource consumers. Syntax certainty and behavioral safety are separate axes.

AST-only architecture is structurally incapable of completing this migration

It cannot reliably recover symbol identity across a workspace, determine effect/resource intent, observe owner/runtime state, place async boundaries, preserve public contracts, or prove SSR/hydration behavior. Use TypeScript semantic analysis, cross-file clustering, runtime diagnostics, and user decisions; use AST/text edits only after a decision exists.

Analysis stack

  • TypeScript programs: symbol provenance, aliases/re-exports, type exposure, tsconfig/project references, JS inference.
  • Syntax trees: stable anchors, JSX shapes, comments/trivia, narrow supported transformations.
  • Workspace graph: package roles, public APIs, renderer/runtime boundaries, topological verification.
  • Solid-specific cluster analyzers: effects, resources, contexts, stores, directives, roots, boundaries, actions.
  • Runtime/source mapping: map diagnostics and scenario failures back to findings and transactions.

Edit engine

  • Rules return edit proposals with semantic preconditions; they never write files.
  • A central engine merges range edits, import changes, JSONC edits, and file creation while detecting conflicts.
  • Prefer range-preserving edits for small changes; use structured printers only for subtrees that require reconstruction.
  • Formatting is a separate touched-file step and is journaled independently from semantic edits.
  • After any manual change, stale findings are invalidated by content/symbol fingerprints and reanalyzed.

Beta.17 error-halt handling

An uncaught reactive error emits REACTIVITY_HALTED and stops later writes/flushes. Error-producing verification scenarios must run in isolated processes/realms, or a controlled test/dev harness must invoke resetErrorHalt() before continuing. Otherwise one expected error invalidates the rest of the run.

Version drift is an invalidation problem

Solid beta “patch” releases can change diagnostics, async semantics, error phases, optimistic pending behavior, SSR/hydration, and package scopes. Rules must declare their supported contracts.

Ruleset bundle

{
  "target": "solid-2.0.0-beta.17",
  "solidCommit": "a51cac193386507f27dd95546f6d567fab4ff6d3",
  "packages": { /* exact compatible Solid and @dom-expressions versions */ },
  "publicContractFingerprint": "sha256:...",
  "diagnostics": [
    "REACTIVE_WRITE_IN_OWNED_SCOPE",
    "ACTION_CALLED_IN_OWNED_SCOPE",
    "SETTLED_CLEANUP_UNOWNED",
    "REACTIVITY_HALTED"
  ],
  "rules": [
    { "id": "solid2.effect", "revision": 4, "targets": ["2.0.0-beta.17"] }
  ]
}

Updating to a new beta

  1. Fetch the new Solid revision and diff docs, changelogs, exports, types, diagnostics, package scopes, and migration examples.
  2. Generate a target-contract delta and identify affected rule IDs and scenario obligations.
  3. Invalidate only findings/decisions whose rules or public fingerprints changed.
  4. Run contract fixtures and real scenarios against the new target before allowing auto-apply.
  5. Keep previous ruleset bundles available so existing runs remain resumable and reproducible.

Fail closed, analyze broadly

An unknown beta may still be inventoried and compared, but deterministic edits require a supported ruleset. This preserves the analyzer’s value without pretending old decisions remain safe.

Implementation roadmap

Each milestone delivers a complete vertical capability. Avoid building a huge rewrite library before the state, transaction, and verification contracts exist.

Target contract + read-only inventory

Implement target locks, workspace discovery, baseline command capture, TypeScript symbol index, capability facets, core Solid surface detectors, durable findings, and the HTML/JSON report projection.

Decision ledger + transactional foundation

Implement decision persistence, change DAG, semantic preconditions, conflict detection, central edit application, journal, forward/reverse patches, reanalysis, resume, and rollback.

Safe mechanical migration

Add exact dependency/config moves, import paths, renderer JSX ownership, proven symbols, and narrow local JSX/store compatibility rules. Every rule ships with source/target contract tests, negative evidence, idempotency, and verification obligations.

Semantic decision workbench

Add cross-file clusters and concrete alternatives for effects, createComputed, resources, stores, lifecycle, roots, directives, async boundaries, and actions/optimistic UX. Persist decisions and generate approved transactions.

Verification feedback system

Add command adapters, browser/SSR/hydration scenario runner, source-mapped Solid diagnostics, beta.17 error-halt isolation, regression attribution, residual-finding generation, and CI mode.

Ecosystem hardening + target updater

Exercise representative app, public library, primitives, component library, SSR/router, custom renderer, and mixed workspaces. Implement target-contract diffing and selective invalidation for future Solid releases.

First concrete engineering sequence

  1. Specify the durable schemas and state transitions before selecting an edit library.
  2. Build target-lock and baseline capture for beta.17.
  3. Build workspace/TypeScript discovery and stable source anchors.
  4. Implement findings for import paths, renderer JSX ownership, effects, resources, and lifecycle—read-only first.
  5. Render a useful report that shows evidence, alternatives, risk, and verification gaps.
  6. Add decisions and the DAG planner.
  7. Add one transactional tracer: dependency/config + import path + typecheck + rollback + idempotency.
  8. Grow deterministic rules only after that tracer proves the whole architecture.

Surprising conclusions

The analyzer is the primary product

Most migration risk is choosing Solid 2 semantics and proving them. Rewriting text is the cheaper downstream operation.

The runtime is part of the specification

Beta.16/17 introduced behavior and diagnostics beyond the stable prose. Documentation-only tooling will drift.

Success is a decision history

A migrated tree is trustworthy when loading, ownership, mutation, SSR, lifecycle, and public API decisions are recorded and verified—not merely when old names disappear.

Independent fresh-context check

A separately tasked planning agent, given only the latest Solid beta.17 source/docs and told to ignore the current repository, independently converged on the same architecture: version-pinned analyzer → evidence-backed decisions → dependency-ordered transactional edits → verification feedback. Its strongest addition was to make the report a projection of an appendable findings/decisions/journal model rather than the source of truth.
