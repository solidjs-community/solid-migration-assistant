Solid has the right migration philosophy—and two competing implementations.

A source-level comparison with the i18n codemod, the React codemod suite, and the current migrations template. The conclusion is less “copy this repo” than “combine the strongest operating model from each.”

What was compared

The peers were selected for different reasons, so repository size is not treated as a quality score. Counts exclude dependencies, Git data, support repos, and report artifacts. Peer test suites were inspected but not rerun; Solid validation was rerun in an isolated Windows mirror because the WSL checkout has only a Windows Node runtime available.

i18n-codemod

Deep, stateful transform

  • One codemod with a 33-file, 6.3k-line internal pipeline.
  • Sharded and regular workflows, rich parameters, workspace semantic analysis.
  • Writes message catalogs, serializes mutation with a mutex, optionally uses LLM key generation.
  • Useful model for modular internals—not for silent error handling or default AI dependence.
react-codemod

Mature suite + recipe

  • 27 self-contained codemods and a thin React 19 recipe.
  • 333 fixture pairs; 264 include expected transform metrics.
  • Root CI, frozen install, Changesets, tagging, and registry publishing.
  • Best structural analogue for Solid’s intended phase packages.
migrations-template

Current operating baseline

  • Gated commit, AI, and publish steps; all expansive actions default off.
  • Semantic analysis in the sample, metrics fixtures, idempotency policy, and agent SKILL.md.
  • Multi-OS fixture CI plus workflow validation before OIDC publication.
  • A process reference, not evidence that its four-case sample is production ready.

The decisive difference: one design, another executable

The root documentation is honest about this split, but the repository still exposes both paths as first-class packages. That makes root tests, recipe semantics, and release intent internally contradictory.

Executable worktree

solid-v2-first-pass

  • Untracked package: zero files exist at HEAD.
  • 1,455-line source transform plus config and validation scripts.
  • 24 fixture pairs across config, source, and validation.
  • Hardcoded Vite/npm/beta.17 application profile.
versus
Committed recipe

Six focused phase packages

  • Correct conceptual boundaries and a thin ordered recipe.
  • All six scripts are explicit async () => null no-ops.
  • 80 fixture pairs specify desired behavior but currently fail when behavior is expected.
  • The shared package exports nothing and only tests that its scaffold loads.
Recommendation: keep the focused-package architecture as the destination, but make only implemented packages runnable or publishable. Port the first-pass tracer bullet into those packages one proven rule cluster at a time; do not maintain a monolith and a duplicate recipe indefinitely.

What Solid should preserve

Keep

The safety vocabulary is a real architectural asset

CONTEXT.md distinguishes safe mechanical work, semantic sites, review-only sites, target profiles, role-aware dependency migration, verification loops, and migration reports. None of the comparison repos makes this contract as explicit.

Keep

Review markers are deterministic and idempotent

Coded TODO(solid-2 ...) markers are safer than speculative rewrites and more auditable than i18n’s catch-and-return-null behavior. They should become structured blockers, not disappear.

Keep

The fixture inventory is already a valuable migration spec

The 80 fixtures attached to the phase packages encode a wide Solid 2 surface. They are useful red specifications; the mistake would be treating their presence as implementation progress.

Keep

Real-repository trials expose semantic closure

Kanban, Solid Primitives, and Solid Router trials test what snapshot suites cannot: dependency topology, type/build closure, runtime behavior, and whether a mechanical patch matches a successful hand migration.

Highest-leverage gaps

These are ordered by how much false confidence they can create, not by implementation effort.

P0

Make one architecture executable

Today the thin recipe composes empty packages while the working implementation is an untracked monolith. Hide the recipe until a stage is real, or port the tracer bullet into phase packages and delete the duplicate path. Package metadata must never imply behavior that its script cannot perform.

Peer signal: React’s recipe delegates only to independently runnable packages; its metadata test also resolves package existence.

P0

Establish a reproducible green floor

Commit the working package, update the lockfile, pin TypeScript/JSSG/Codemod CLI versions, fix the two red first-pass cases, and either implement or exclude no-op packages from the root green gate. Add CI for frozen install, type checks, fixture tests, and workflow validation.

Current evidence: frozen install fails; root types fail; first-pass source is 18/20; imports is 1/9.

P0

Move safety decisions from names to bindings

The failing local-name collision fixture proves that import-aware helpers do not protect the whole global text pipeline. Use AST nodes and binding provenance for every rule whose safety depends on symbol origin. Enable workspace semantic analysis only for phases that truly need cross-file definitions or references.

Borrow from i18n’s selector-oriented decomposition and the template’s semantic-analysis requirement; retain fail-closed behavior.

P1

Turn the domain model into a workflow graph

Add discovery/classification before edits, then deterministic transforms, structured validation/reporting, an opt-in semantic/AI phase, and project-level verification. Target Profile and Compatibility Manifest should become actual inputs/state instead of glossary-only concepts.

P1

Measure transformations and blockers

Add metric atoms per rule family and cardinality for applied, skipped, ambiguous, and blocked sites. Store metrics.json expectations beside fixtures. Generate a machine-readable Migration Report with evidence and required verification.

P2

Add publishing machinery only after correctness gates

Use React’s release flow and the template’s workflow validation, agent skill, and gated publish parameters. Avoid copying “publish first” boilerplate into a repository whose primary contract is still red.

Recommended target architecture

The key is staged evidence. Each phase should either produce safe edits, a structured blocker, or no change—never silent partial success.

01

Discover

Workspace/package roles, package manager, Solid/compiler/renderer versions, target profile, SSR, public-library boundaries.

02

Transform

Focused JSON/import/type/JSX/runtime packages. AST and binding-aware. Each package independently runnable and tested.

03

Validate + report

Parse touched files, validate imports and blocker budget, emit rule metrics and a Migration Report. Fail closed.

04

Resolve semantics

Optional AI/manual work queues for resource clusters, effects, ownership, lifecycle, and public API decisions.

05

Verify

Install, types, build, unit/E2E, diagnostics, and second-pass hashes. Compare supported corpora against expected outcomes.

Package boundaries

Use React’s focused-package + thin-recipe pattern. Inside a genuinely complex phase, use i18n’s internal split into selectors, processors, domain types, and emitters. Move helpers into @solid-codemod/shared only after two implemented packages need the same stable behavior.

Workflow defaults

Deterministic edits and validation run by default. AI, per-step commits, branch pushes, and PR creation remain off unless explicitly enabled. A review marker is a blocker when the selected completion policy requires a closed migration.

Recommended execution order

P0 · now

Choose and green the executable path

Track solid-v2-first-pass; fix collision and nested-flush regressions; pin tool versions; update lockfile; make frozen install and root checks pass. Remove recipe visibility or implement its first real phase.

Exit criterionFresh clone + frozen install + root CI passes; every advertised codemod changes at least one positive fixture and preserves a no-op fixture.
P0 · next

Extract imports/config as the first tracer-bullet phases

They are the safest boundaries and already have 24 specifications. Port implementation from first-pass, add binding-aware selectors, and make the recipe temporarily contain only these green packages.

Exit criterionFocused packages pass fixtures, metrics, workflow validation, and a small Vite app trial independently and through the recipe.
P1

Add discovery, structured blockers, and corpus gates

Materialize Target Profile and Compatibility Manifest; emit a Migration Report; run Kanban automatically and Router/Primitives as expected-blocker corpora with stable budgets.

Exit criterionNo workflow success when syntax/import/blocker postconditions fail; one- and two-pass hashes are tested; blocker counts are explainable.
P1

Port JSX/runtime rule clusters incrementally

Split by safety class and provenance needs. Keep semantic effect/resource/ownership work out of safe packages; feed it into an explicit review queue.

Exit criterionEach cluster has positive, negative, collision, alias, formatting, and idempotency fixtures plus a real-project acceptance case.
P2

Operationalize and publish

Add package skills, contributor policy, Changesets/tagging, multi-OS CI where relevant, registry publishing, and opt-in AI/PR workflow nodes.

Exit criterionA tagged recipe can be installed from scratch, produces a truthful report, and is blocked from publication unless every declared package contract passes.

Borrow selectively

Adopt

  • React: independent packages, thin recipe, fixture metrics, frozen CI, Changesets/release path.
  • i18n: internal modules by concern, selector-first entry, parameter schemas, serial execution when side effects require it.
  • Template: semantic-analysis rule, idempotency policy, gated AI/commit/publish, workflow validation, package skill.
  • Solid: domain language, fail-closed review markers, compatibility/target concepts, corpus verification.

Do not copy blindly

  • i18n’s catch-and-return-null failure path or AI review as a substitute for deterministic correctness.
  • @latest tool execution in a migration product that needs replayable output.
  • Template publishing machinery before a green correctness contract.
  • React’s raw package count as a goal; split only where packages are independently useful and testable.
  • Fixture volume as a readiness metric when the attached transform is a no-op.
