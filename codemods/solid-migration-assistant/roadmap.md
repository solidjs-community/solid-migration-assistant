# Solid Migration Assistant roadmap

Target: a clean analyzer run should mean that the scanned project is ready for the pinned Solid `2.0.0-beta.34`, not merely that no currently supported pattern was found. The workflow remains read-only.

- [ ] **Define the readiness contract.** Report one of `findings`, `blocked`, or `ready`; never report `ready` after parse errors, unresolved project analysis, unsupported files, missing configuration, or skipped workspaces. State the exact Solid beta and project boundary checked.
- [ ] **Cover configuration, packages, and imports.** Check `package.json`, lockfiles, `tsconfig`/JSX configuration, renderer packages, JSX type ownership, type imports, re-exports, dynamic imports, `require`, and all legacy Solid subpaths.
- [ ] **Cover the complete beta.34 migration guide.** Add detectors for batching and synchronous reads; every effect, lifecycle, cleanup, and dev-diagnostic change; `/*@once*/`; resources, transitions, and async APIs; remaining store/props changes; control-flow and dynamic-component changes; DOM behavior including `class:`, `style:`, `attr:`, `bool:`, `on:`, `oncapture:`, directives, and delegated events; context-provider changes; and every rename/removal in the guide's quick map.
- [ ] **Close gaps in existing rules.** Support aliases, namespace imports, supported overloads, forwarded/spread forms, JSX closing/import sites, and other currently excluded syntax without weakening binding resolution or producing speculative guidance.
- [ ] **Scan the whole project.** Analyze JavaScript, JSX, TypeScript, and TSX plus monorepo workspaces, SSR entry points, configuration, and relevant dependency usage. Build a project graph for cross-file aliases, wrappers, exports, and indirect calls.
- [ ] **Prove semantic readiness.** Detect behavior-sensitive hazards such as post-setter reads, top-level reactive reads, writes in tracked scopes, cleanup timing, mutable-store writes, resource tuple use, and changed control-flow callback shapes. When static proof is impossible, emit a blocking finding rather than silently passing.
- [ ] **Run read-only compatibility validation.** In a disposable copy, install the pinned Solid beta and run the project's typecheck, build, and declared test commands; treat failures, missing validation commands, or created persistent artifacts as blockers.
- [ ] **Make coverage measurable.** Maintain a machine-readable inventory mapping every official migration-guide item to a detector or readiness gate. Require positive, negative, alias, namespace, shadowing, overload, and unsupported-case fixtures; test real Solid 1 applications and mutation-seeded migration sites to measure false negatives.
- [ ] **Track beta drift.** On every new Solid beta, diff packages, exports, types, migration documentation, and runtime behavior; fail readiness checks until the inventory, detectors, fixtures, and version pin are reviewed and updated.
- [ ] **Keep the guarantee honest.** Document `ready` as: no known beta.34 migration sites, no skipped or unsupported project surface, and successful compatibility validation. Do not claim readiness from detection alone when runtime behavior is unobservable.
